# 开发任务按需查阅

## 上游与依赖

- 设计复杂功能时（如同步歌词、播放队列或跨组件交互），主动到 GitHub 查阅相关上游项目的实现或官方文档，再结合 FitBay 的现有能力选方案。在对应任务记录中附上参考链接和采纳理由；复用代码或引入依赖前核对许可证。
- 沿用 Electron、React、TypeScript、Vite 和 Dockview。依赖用 `npm ci` 安装；增删升级前核查必要性、维护情况和许可证，并同步锁文件。
- 选择参考项目或第三方依赖时，功能和维护情况相当的，优先采用 MIT、Apache-2.0、BSD-2-Clause、BSD-3-Clause、ISC 等宽松许可证的项目。实际复用时，按所用版本核对代码和随附资源的许可，在线服务另查商用条款。

## 宿主与界面

- 新增或修改 FitBay 界面时，复用 Music 的公共控件，从首次显示就使用 Fluent 固定深色玻璃。页面、设置、表单和弹层继承公共主题，独立 React 入口接入 `ComponentTheme`。改动交互时按[日常操作](../../设计规范.md#日常操作)走通用户路径，涉及[下拉框与菜单](../../设计规范.md#下拉框与菜单)时从实际入口展开验收。
- 公共宿主方案 B 用于示例与第一方音乐试听组件。遵循[组件开发](../../组件开发.md)和[架构说明](../../架构说明.md)，不提前搭建数据库、AI 执行层、插件 SDK 或空接口。
- 系统能力经专用 preload 接口提供，主进程校验输入。禁止暴露通用 IPC、任意系统操作或凭据。私人数据按[数据与交付](../../数据与交付.md)处理。

## 修复与交付

- 修 bug 先复现，修完从相同起始状态按原步骤复验。小修由主代理自查；高风险改动默认开一个不继承实现讨论的只读子代理做一次全面审核，主代理逐项复核。详见[独立审核与缺陷复验](../../开发流程.md#独立审核与缺陷复验)。
- 修复后只复核原问题和直接受影响的行为。可复现且违反本次验收条件的问题，以及确认由本次改动引入的回归，在本轮处理；其他建议记待办。约定的检查和回归用例通过、已确认的阻塞缺陷清零，即结束本轮代码审核。
- 先集中完成本次能在后台执行的检查，使用独立 profile，不抢焦点。代码或配置改动运行 `npm run check`；纯文档核对格式、链接和事实；视觉改动检查真实运行截图。
- 每个独立事项实现、验证并同步现行文档后，审阅工作区及暂存 diff，仅提交该事项。记录实际结果、限制和 commit；最后一项可先用唯一提交主题定位，下次补编号。交付时分别报告本地检查、远程 CI 和人工验收的实际状态。
- 组件组负责本组件小修验收，按影响核对独立与停靠入口。
