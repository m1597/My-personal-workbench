# Design

## Context

日常窗口与示例视图属于不同 Electron 主进程。原型的原生命中测试只识别本进程中已打开的 shell，使用标题栏中心点和整个工作区矩形。当前分离依赖内容上方的专用拖动手柄。日常布局读取器只接受内置模块，直接保存临时组件会让下次启动回退默认排列。

## Goals / Non-Goals

目标是同一工作台、双向拖放和会话连续。先支持 Windows 上的内置示例。音乐、任意外部程序嵌入及第三方组件分发继续按既有计划推进。

## Decisions

1. 两个桌面入口交给同一公共宿主进程，单实例按用户范围识别。再次启动只转交受限的“打开工作台”或“打开示例”意图，宿主决定部署路径和组件白名单。先启动组件时只创建组件窗口，随后打开工作台时再创建 shell。无需将跨进程 HWND 嵌入现有面板。
2. 保留日常工作台的 profile、页面来源与布局键。原型测试继续用临时 profile。组件保持独立受限 session。布局读取兼容原四模块与空布局，组件引用缺失时只处理该引用，不能重置其余布局。
3. 原生移动期间以实际指针的屏幕 DIP 坐标和可见目标组计算预览，结束时重新验证目标、遮挡与取消状态。Dockview 中心创建标签，边缘按方向创建分屏；空工作区创建首个组。预览与提交共用同一命中结果。
4. 从组件标签开始拖动时记录组件与原组。工作台内保留 Dockview 拖放；在窗口外松手时由宿主接回原 WebContentsView 并创建独立系统窗口，在可见屏幕区域定位。先完成视图交接再清理旧标签，失败保留原位置，避免关闭回调误销毁会话。

## Risks / Trade-offs

Chromium 标签拖动在工作台外释放可能收不到普通 pointerup。先在独立 Windows 桌面验证 Dockview 拖动结束事件与原生指针位置；若拿不到可靠的释放或取消信号，需要补充受限宿主事件，再决定交互可交付。覆盖混合 DPI、负坐标、窗口遮挡、两种启动顺序、拖出后取消和进程退出。模拟 Windows 消息只能证明状态机和布局结果。
